# multilingual-e5-small next to grande

2026-09-21. [intfloat/multilingual-e5-small](https://huggingface.co/intfloat/multilingual-e5-small)
(MIT) is a 118M-parameter sentence-embedding model: 12 BERT layers of
width 384 (21.6M non-embedding parameters) under XLM-R's 250k-token
vocabulary (96M parameters of embedding table). It has no head at all — it
maps a text to a unit vector — so where [Laya](laya.md) was measured as a
model that answers questions, e5 is measured as a backbone: frozen vectors
plus a head trained in seconds, and, for the ceiling, the whole encoder
fine-tuned on the task. Same JGLUE evals, same protocol as
[comparison.md](comparison.md) and [laya.md](laya.md), same M4.

Scripts: `tools/e5_features.py` (embed the four splits, batch-1 latency),
`tools/e5_head.py` (heads on frozen vectors), `tools/e5_generic.py` (one
head for any choice question), `tools/e5_finetune.py` (full fine-tune),
`tools/e5_serve.py` (`/v1/systemone` shim). Results: `runs/e5/`.

## Setup

Every text is embedded as e5 wants for a symmetric task, `query: …`, masked
mean pooling, L2-normalised. For a JNLI record the premise `u` and the
hypothesis `v` are embedded separately and also as one sequence
`query: 前提: … 仮説: …` (`pair`); for a JCommonsenseQA record the question
`q`, each choice `c` and each `query: 質問: … 答え: …` (`joint`). Heads:

| head | input | trainable |
|---|---|---|
| `cos` | zero-shot: cos(u, v) with two thresholds (JNLI), argmax cos(q, c) (JCQA) | 2 thresholds / 1 temperature |
| `sep-lr`, `sep-mlp` | [u, v, \|u−v\|, u∗v] → 3 logits (JNLI); per choice [q, c, \|q−c\|, q∗c] → score (JCQA) | 4.6k / 0.8M |
| `pair-*`, `joint-mlp` | the pair / joint sequence embedding | 1k–0.2M |
| `both-mlp` | both of the above | 1.0M |
| `generic` | one head for both tasks: [s, o, \|s−o\|, s∗o] for the rendered state `s` and each option's description `o`, softmax over a question's options — what `e5_serve.py` serves | 0.8M |
| `ft` | the whole encoder fine-tuned as a cross-encoder (JNLI: pair → 3; JCQA: joint → score), 3 epochs, lr 3e-5, ~35 / ~55 min on the M4 | 118M |

Heads train on the JGLUE train split (JNLI 20,073, JCQA 8,939); the last
10 % of train picks the epoch. Temperature is fitted on the even-indexed
valid records and everything is reported on the odd-indexed ones
(n = 1,217 / 559), plus the first 400 rows raw, the rows the README's
trained-head numbers use. Latency is PyTorch fp16 on MPS at batch 1,
tokenisation included, one forward per record.

## Reading

- **Frozen e5 + a 0.8M head beats laya-multilingual on both tasks** at the
  same latency: JNLI 0.758 vs 0.702, JCQA 0.665 vs 0.551. The 118M
  embedding model with a head trained in seconds is a better Japanese
  System One than the 322M RL-trained decision model. The zero-shot rows
  say why: cos(premise, hypothesis) alone sorts JNLI at 0.656 (above
  zero-shot E2B's 0.614), and argmax cos(question, choice) gets 0.635 on
  a 5-way commonsense set — e5 was trained on enough Japanese pairs that
  the geometry already carries most of the signal, and the head mostly
  learns which direction is "contradiction".
- **It does not reach grande's numbers.** JNLI 0.759 is 9 points under the
  frozen E2B + pointer head (0.848) and JCQA 0.665 is 19 points under
  zero-shot E2B (0.853): a 384-wide vector of the question cannot hold the
  world knowledge a 2B decoder reads out, and the head cannot add it. The
  fine-tuned rows put the ceiling of the encoder itself: **JNLI 0.831**
  (first 400: 0.835, 1.3 points under E2B + head at 1/20 of the latency;
  the README's "fine-tuned encoders reach about 0.90" is for base-sized
  models) and **JCQA 0.671** — fine-tuning the whole encoder on 9k
  commonsense questions adds 0.6 points over the frozen head. NLI is a
  skill a 21M-parameter encoder can learn; commonsense QA is knowledge it
  does not have, and no head or fine-tune puts it there.
- **Separate embeddings beat the joint sequence** for a frozen model
  (`sep` 0.758 / 0.665 vs `pair` / `joint` 0.71 / 0.59): e5 was trained on
  pairs, so |u−v| and u∗v are the features it knows how to produce, and a
  single sequence with two sentences in it is out of distribution for its
  pooling. That is also why the `generic` head (which has to read the
  state as one sequence) gives up 4 points on each task; it is still above
  Laya on both.
- **Calibration is a non-issue.** Trained heads come out at ECE 0.02–0.06
  raw with T ≈ 1.2–1.4, against 0.21–0.25 raw for Laya and zero-shot E2B;
  a softmax head trained with cross-entropy on 20k rows is calibrated by
  construction. The zero-shot `cos` on JCQA needs T = 0.08 (cosines sit
  in [0.85, 1]) and is still at ECE 0.33 after it.
- **Latency is the runtime, not the model.** 16–22 ms per record is
  PyTorch's per-call overhead on MPS at batch 1 (the same ceiling
  laya-mlx sits under); the model is 21.6M non-embedding parameters,
  ~2 GFLOP per record; the same runtime overhead is what the shim's
  12–17 ms per request is made of — see below.

## As a grande backend

`tools/e5_serve.py` serves the `generic` head behind `/v1/systemone`
(`--head runs/e5/generic/head.pt`): the rendered state (`key: value`
pairs) and every option description the server has not seen go through
the encoder as one batch, the head scores each (state, option) pair, and a
softmax over a question's options is the answer. Any choice / noul / score
request works; only choice questions were in the training data, so noul
and score answers are untrained. Measured through `tools/http_eval.py`
(caller wall time over localhost, GPU otherwise idle): JNLI full valid
0.712 / ECE 0.031 at **14.7 ms** per record, JCQA 0.616 / ECE 0.045 at
**16.7 ms**, `examples/ticket-ja.json` (5 questions, 220 tokens) **12 ms**
min / 13 ms median (Laya: 18 / 21 ms per record, 24 ms for a 3-question
request through laya-mlx; grande E2B ~700 ms). Option vectors are cached
across requests (criteria are fixed text), so a request costs one forward
of the state plus whatever options it has not seen; without the cache the
JNLI record was 47 ms.

What a port onto `grande-wgpu` would need: BERT is simpler than the mmBERT
Laya already runs there (absolute position embeddings added in the
embedding gather, post-LayerNorm, full bidirectional attention, no RoPE,
no local layers), and the head is 0.8M parameters of MLP on the host; the
vocabulary prunes the same way as Laya's (250k → the corpus's tokens).
The weights would be ~22 MB at Q8 plus the pruned embedding (~20 MB for a
56k vocabulary); with Laya's 110M-parameter encoder at 44 ms for a
3-question request on that engine, e5's 21.6M should land under 10 ms. The
alternative in the browser is transformers.js, which already ships
`Xenova/multilingual-e5-small` (ONNX, WebGPU); the head is a few lines of
JavaScript on top. Whether either is worth doing depends on what the
numbers above are for: as a fast first tier that escalates to E2B / E4B on
low confidence e5 + head is the cheapest option measured so far; as a
replacement for the LLM readout it is not one.

## Rerun

```bash
PY=python/.venv/bin/python
$PY tools/e5_features.py --out runs/e5 --latency 200         # ~10 min on the M4 (HF_HUB_OFFLINE=1 once the model is cached)
$PY tools/e5_head.py --feat runs/e5 --out runs/e5/summary.json
$PY tools/e5_generic.py --feat runs/e5 --out runs/e5/generic
$PY tools/e5_finetune.py --task jnli --out runs/e5/ft-jnli   # ~35 min
$PY tools/e5_finetune.py --task jcqa --out runs/e5/ft-jcqa --bs 8   # ~55 min; 8 records = 40 sequences, 32 needs >13 GB on MPS
$PY tools/e5_serve.py --head runs/e5/generic/head.pt --port 8792
$PY tools/http_eval.py --url http://127.0.0.1:8792 --task jnli
```
